# Learning OS — Domain Model

This document defines the canonical domain model used by the application.

## 1. Design rules

- Domain objects must not depend on FastAPI, React, Obsidian, SQLite, or a specific AI provider.
- Every persistent entity has a stable UUID/ULID-like `id`.
- Timestamps are UTC ISO-8601.
- Domain state transitions are explicit.
- Raw learning evidence is immutable; derived scores may be recalculated.
- Markdown files and database records are linked by stable IDs, never filenames.

---

## 3. LearningGoal

```yaml
id: goal_...
title: string
description: string?
domain: string?
target_level: beginner|intermediate|advanced|professional
status: draft|active|paused|completed|archived
priority: 1..5
deadline: datetime?
available_minutes_per_week: integer?
created_at: datetime
updated_at: datetime
```

Invariants:

- `title` is required.
- Only one primary roadmap is active per goal.
- A completed goal is read-only except for retrospective notes.

---

## 4. Concept

A concept is the smallest useful knowledge unit that can be taught, assessed, linked, and reviewed independently.

```yaml
id: concept_...
title: string
domain: string
status: unknown|learning|weak|developing|usable|strong|mastered|needs_review|deprecated
mastery: 0.0..5.0
confidence: 0..100
importance: 1..5
retention: 0..100
last_practiced: datetime?
next_review: datetime?
obsidian_path: string?
created_at: datetime
updated_at: datetime
```

Invariants:

- `mastery` is derived from evidence and may not be arbitrarily set by an AI response.
- `confidence` represents user-reported or inferred confidence and must remain separate from mastery.
- `importance` belongs to the learning goal context; a future version may allow goal-specific importance.

---

## 5. Skill

A skill describes something the user can perform.

Examples:

```text
write_window_function
optimize_bigquery_query
debug_python_pipeline
design_etl_pipeline
```

```yaml
id: skill_...
title: string
description: string
mastery: 0..5
concept_ids: []
```

A skill can depend on multiple concepts.

## 6. Evidence

Evidence is immutable proof generated by a learning interaction.

```yaml
id: evidence_...
concept_id: string
skill_ids: []
goal_id: string
session_id: string?
activity_id: string
source_type: exercise|assessment|teach_back|project|review|self_report
difficulty: 1..5
correctness: 0..1
reasoning: 0..1
independence: 0..1
transfer: 0..1
confidence: 0..1
timestamp: datetime
metadata: object
```

Evidence is never edited after creation.

## 13. Activity

```yaml
id: activity_...
session_id: string
type: recall|explanation|example|exercise|feedback|reflection|review|project_task|assessment
sequence: integer
concept_ids: []
status: pending|active|completed|skipped
exercise_id: string?
```

`exercise_id` was added during T103 -- an `exercise`-type Activity is
paired with an AI-generated `Exercise` when `POST /sessions/{id}/next`
creates it, but nothing recorded which one; `POST
/sessions/{id}/activities/{id}/answer` needs the `exercise_id` to call
`AnswerSubmissionService` (which takes `exercise_id`, not `activity_id`)
and the entity had no field to carry that link across the two requests.

## 17. State transitions

### Goal

```text
draft → active → paused → active
active → completed
active → archived
paused → archived
```

### Concept

Concept status is derived from mastery + review state:

```text
unknown
→ learning
→ developing
→ usable
→ strong
→ mastered
```

Weak evidence can move a concept to `weak` or `needs_review`.

### Session

```text
planned → active → completed
planned → abandoned
active → abandoned
```

Invalid transitions must be rejected by the domain layer.

---

## 18. Mastery calculation

MVP:

```text
performance =
    0.35 * recent_performance +
    0.20 * historical_performance +
    0.20 * transfer_performance +
    0.15 * independence +
    0.10 * retention
```

Normalize all inputs to `0..1`, then map to `0..5`.

Weights are configuration, not business logic constants.

The system must retain raw evidence.

---

## 19. Next-activity scoring

Each candidate activity receives:

```text
priority =
    importance
    * weakness
    * prerequisite_factor
    * review_factor
    * mistake_factor
    * transfer_factor
```

The implementation may refine the formula, but selection must remain explainable.
